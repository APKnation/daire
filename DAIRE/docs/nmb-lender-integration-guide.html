1 · Integration model — one trusted network, keyless JSON

All DAIRE subsystems — the NMB lender subsystem, the DAIRE Central System, the AI engine and the blockchain bridge — run on the same trusted network. Inter-system calls are therefore plain HTTP + JSON without API keys or bearer tokens.

You do not need to implement any authentication for the demo. Send and accept plain JSON. Central is configured with REQUIRE_API_KEYS=false. If a subsystem is ever exposed beyond the LAN, Central switches that flag on and every call must then carry X-API-Key — build your receive endpoint so adding header checks later is a one-line change.
DirectionCallAuth for demo
Central → NMBGET {nmb_base}/borrowers?borrower_reference=…none
NMB → CentralPOST http://172.17.16.76:8000/api/lender-data/receive/none
Central → NMBPOST {nmb_base}/api/daire/central/receive/ (result broadcast)none

2 · What NMB must expose — GET /borrowers

Central calls this endpoint to pull one borrower's data. Register your base URL (e.g. http://172.17.16.70:9000) with Central; Central appends the path itself.

GET /borrowers?borrower_reference=1001
Accept: application/json

Rules the endpoint must follow:

  • Match only on the exact borrower_reference — return that customer's record, never another customer's.
  • Return 200 with the JSON contract in section 3, or 404 with the body below when the reference is unknown to NMB. Never return an empty 200.
  • Send null for unknown values — never guess 0. A guess overwrites a real value as "latest" during conflict resolution.
  • Dates ISO YYYY-MM-DD, datetimes with Z, money as JSON numbers (max 4 decimals), currency TZS in source_metadata.currency.
  • All identifiers are plain numbers. Customer ids are zero-padded digits — 001, 002, 003 (no prefixes like NMB-CUST-). Account, loan, repayment and transaction ids are digit-only too (3001, 4001, 5001, 6001). Send them as JSON numbers or digit-only strings — Central accepts both and normalizes.
  • Support audit logging for every data pull (who asked, what was shared, when).
404 Not Found
{ "detail": "Borrower not found", "borrower_reference": "1001" }

FieldRequiredMeaning

Loan status ∈ ACTIVE, CURRENT, OPEN, COMPLETED, CLOSED, DEFAULTED, WRITTEN_OFF. Repayment status ∈ ON_TIME, LATE, MISSED, DEFAULTED. Never send PINs, passwords, card security codes or full tokens.

4 · What NMB calls — push to Central

NMB can push a borrower directly instead of waiting for a pull. Keyless — just JSON.

POST http://172.17.16.76:8000/api/lender-data/receive/
Content-Type: application/json

{
  "lender_id": "NMB-001",
  "borrower_reference": "1001",
  "account_reference": "3001",
  "payload": {
    "borrower_reference": "1001",
    "customer_id": "001",
    "transaction_count": 240,
    "transaction_total_amount": 18400000.0,
    "transaction_currency": "TZS",
    "income_count": 24,
    "income_total_amount": 14400000.0,
    "transaction_period_start": "2024-02-01",
    "transaction_period_end": "2025-01-31",
    "loans": []
  }
}
Send aggregates, not thousands of rows. transaction_count + transaction_total_amount (+ income counts/totals) are enough for scoring; Central derives the same aggregates automatically if a transactions array is sent instead. payload.loans must always be a list ([] when none) and the borrower_reference inside payload must equal the top-level one.

Success response (201)

{
  "status": "COMPLETED",
  "lender_id": "NMB-001",
  "borrower_reference": "1001",
  "summary": {
    "transaction_count": 240, "transaction_total_amount": 18400000.0,
    "transaction_currency": "TZS", "income_count": 24,
    "income_total_amount": 14400000.0,
    "total_loans_for_borrower": 1, "active_loans": 1
  },
  "borrower": { "…merged unified borrower record…" }
}

Conflicts are expected. When two lenders disagree on identity fields (age, income, …), Central keeps both: latest push wins, the losing value is preserved in data_conflicts. Loans / repayments / transactions never conflict — they are keyed per lender + ID and added together. Push null when a value is unknown so a guess never overwrites a real value.

5 · What NMB receives — credit result broadcast

After AI and blockchain scoring finish, Central pushes the final credit result to every lender linked to the borrower — including NMB, at the fixed receive path below. Expose one POST handler there.

POST {nmb_base}/api/daire/central/receive/
Content-Type: application/json
{
  "result_type": "CREDIT_RESULT",
  "borrower_reference": "001",        // ← NMB's own customer id
  "central_borrower_reference": "1001",  // central unified reference (audit only)
  "lender_customer_id": "001",
  "assessment_reference": "ASM-2026-0005",
  "result": {
    "kind": "BLOCKCHAIN_SCORE",
    "generated_at": "2026-09-18T10:35:00Z",
    "credit_score": 652,                        // public 350–800 scale
    "risk_band": "FAIR",
    "transaction_hash": "0xabc123…", "block_number": 152300
  },
  "results": {
    "ai": {
      "reputation": "EXCELLENT",
      "score": "0.9450",                        // decimal string — parse as decimal
      "risk_level": "LOW",
      "behavior_summary": "Borrower shows consistent on-time repayments…",
      "model_version": "credit-risk-joblib-v1"
    },
    "blockchain": {
      "credit_score": 652,
      "risk_band": "FAIR",
      "contract_address": "0xabc123…",
      "transaction_hash": "0xabc123…", "block_number": 152300
    }
  }
}

What your endpoint must do:

  1. Look up your customer by borrower_reference — ignore results for references you do not hold (log the attempt, reply 404).
  2. Store or display the result for that customer only. Central sends derived scores only — never raw transactions or balances.
  3. Reply 200 with any JSON acknowledgement, e.g.:
{ "received": true, "lender_system": "NMB", "result_type": "CREDIT_RESULT", "score": 652 }

Demo flow

1 · NMB pushes borrower
(or Central pulls)		→ 2 · Central merges
all lender data		→ 3 · AI reputation
+ blockchain score		→ 4 · Result broadcast
back to NMB
  1. Data in. NMB pushes POST /api/lender-data/receive/ — or Central pulls POST /api/borrowers/pull-from-all-lenders/ {"borrower_reference": "1001"}, which calls GET {nmb_base}/borrowers?borrower_reference=….
  2. Merge. Central normalizes the payload into the unified borrower (accounts, loans, repayments, financial profile) and records a DataExchange audit entry.
  3. Score. An assessment opens on the merged borrower; the AI engine returns a reputation (0–1) and the smart contract records the credit score (350–800) on-chain.
  4. Result out. Central broadcasts the combined result to NMB's /api/daire/central/receive/ endpoint.

7 · Error behaviour, audit and security rules

SituationNMB returns
Borrower unknown at NMB404 + { "detail": "Borrower not found", "borrower_reference": "…" }
Malformed request (missing reference)400
Temporary outage / dependency down503
Later, if keys are switched on: missing/invalid credential401
  • Never return a successful response containing a different customer's records.
  • Verify consent / legal basis before releasing data; log an audit event for every pull (borrower reference, requester, purpose, fields shared, timestamps, correlation id).
  • Duplicate pushes are safe — Central keys records by lender_id + stable IDs, so re-sending the same borrower does not create duplicates (as long as loan_id / account_reference are stable).
  • Use TLS when traffic leaves the trusted LAN, keep service accounts least-privileged, and never commit credentials or customer data to source control.

9 · Borrower portal loan application — what the borrower fills in

When a borrower applies for a loan in the borrower portal, they complete only identity, declaration, loan request and consent. They never re-type their financial history — that arrives automatically from the bank (section 10).

GroupFields the borrower provides
IdentityNIDA number, full name, date of birth (→ age), gender, phone (OTP-verified), email.
EmploymentEmployment status (EMPLOYED / SELF_EMPLOYED / BUSINESS_OWNER / UNEMPLOYED), employer name, declared monthly income.
Business (if any)Business name, type (RETAIL / AGRICULTURE / SERVICES …), BRELA registration number, business start date.
Loan requestRequested amount, purpose (BUSINESS / EDUCATION / AGRICULTURE / HOME …), duration in months, preferred repayment date.
ConsentExplicit consent for DAIRE to pull data from lenders — purpose + expiry (stored in the existing Consent model).
Documents (optional in demo)ID scan, payslip, bank statement.

11 · Merged borrower database — where every field lands in Central

Central merges both sources into one unified borrower record. Matching is only on exact borrower_reference; financial records are additive (keyed per lender + stable IDs); identity disagreements are logged in data_conflicts (latest push wins) and never silently lost.

Demo note: Central has no LoanApplication model — the loan request lives in the portal/bank. A portal app uses the existing endpoints (register borrower → receive/pull → assessment → broadcast) and keeps the application form on its side. The final result reaches the borrower via the broadcast in section 5, and the borrower sees the reputation + 350–800 score in the portal.
